# Geomap 门店网络决策平台产品与开发规划

> 规划基线：v3.0.2
> 更新日期：2026-08-17
> 规划版本：v1.1（融合经营时间轴与自定义选址模型）
> 状态：产品方向建议稿，供 UI 设计、数据建模和版本排期使用

## 实施状态（2026-08-17）

- `v3.1.0-beta.1`：管理层总览与门店网络。
- `v3.2.0-beta.1`：全历史式经营时间与统一记录。
- `v3.3.0-beta.1`：可配置、可解释、可版本化的选址模型。
- `v3.4.0-beta.1`：经营数据接入、指标口径与质量中心。
- `v4.0.0-beta.1`：公开/私有分层、企业角色、版本协作、评论、分享和审计。

上述 beta 均保持 Full/Lite、GeoJSON、Pages 和离线单文件兼容；v4 私有服务的生产边界见 [`V4_PRIVATE_DEPLOYMENT.md`](V4_PRIVATE_DEPLOYMENT.md)。

## 1. 结论

Geomap 不应继续以“GeoJSON 地图编辑器”作为主要产品心智。建议将它定位为：

> 以门店网络为核心，把经营现状、事件、发展历史、候选选址模型和决策依据放在同一张可回放的时空地图中的管理决策工作台。

产品首先帮助管理层回答四个问题：

| 决策问题         | 产品回答                                               |
| ---------------- | ------------------------------------------------------ |
| 现在怎么样？     | 门店规模、区域覆盖、状态、经营表现、异常和数据更新时间 |
| 哪里有机会？     | 空白区域、潜力商圈、低覆盖区域、竞品与客群分布         |
| 该选哪个点？     | 候选点评分、商圈覆盖、成本、竞争、蚕食风险和可解释排名 |
| 过去发生了什么？ | 开关店、状态变化、经营趋势、重大事件、决策与结果复盘   |

地图编辑、图层、绘图、导入导出仍然重要，但应作为分析和数据维护能力出现，而不是占据首屏。

产品由两个相互连接的核心引擎组成：

1. **经营时空引擎**：像历史地图产品查看王朝和事件一样，选择或拖动时间，地图、门店状态、事件和经营数据一起变化；经营者也能直接在某个时间点或时间段录入事实。
2. **选址模型引擎**：用户可自行定义指标、数据来源、计算规则、权重、阈值和适用范围，形成可复用、可版本化、可解释的选址模型。

两者必须互通：历史经营结果可用于校准选址模型，选址时的假设和决策又会成为未来可复盘的经营事件。

## 2. 当前产品诊断

### 2.1 可直接继承的资产

- Leaflet 地图、点线面绘制、范围圈、底图和标记样式。
- GeoJSON、CSV、Excel 导入导出及单文件离线分发。
- 图层显隐、搜索、表格联动、聚合、自定义组。
- 快照、浏览模式和事件记录的初步能力。
- Full/Lite、Pages、离线单文件和 TypeScript 渐进迁移基础。
- 输入净化、版本化工作区和自动化测试的工程基础。

### 2.2 与管理决策场景的主要差距

| 层面     | 当前状态                                             | 对用户的影响                                |
| -------- | ---------------------------------------------------- | ------------------------------------------- |
| 产品语言 | 首页围绕“地图控制、图层、绘图、GeoJSON”              | 管理层需要先理解 GIS 工具，才能找到业务答案 |
| 首屏重点 | 左侧控制面板和右侧图层面板占据大量地图空间           | 看不到经营概览、异常、机会和明确下一步      |
| 功能入口 | 清空、导出、分享等能力在多个区域重复出现             | 入口选择成本高，危险操作过于靠前            |
| 信息层级 | 缩放、聚合、标签、底图与业务功能同级                 | 高频决策与低频设置混在一起                  |
| 看板     | 目前只统计标记总数和类型                             | 不能回答门店表现、目标达成、趋势和区域差异  |
| 历史     | 快照可切换，但没有连续时间、业务事件和指标联动       | 只能“回到某一版”，不能沿时间理解经营过程    |
| 录入     | 事件、快照、属性和数据分散在不同入口                 | 经营者无法自然记录“何时、何地、发生了什么”  |
| 选址     | 有范围圈、绘图和属性编辑，但没有自定义模型体系       | 不能复用企业方法、比较模型或沉淀选址结论    |
| 数据     | 导入以文件格式为中心，缺少业务字段映射和数据质量反馈 | 后续经营数据接入会迅速变得不可维护          |
| 协作     | 截图和小数据链接分享为主                             | 无评论、审批、结论、责任人和审计记录        |
| 状态管理 | 旧功能分散使用多个 localStorage 键                   | 数据一致性、迁移和备份风险较高              |

代码现状也限制了 UI 的继续叠加：`script.js` 约 5,500 行、`style.css` 约 6,400 行，HTML 仍有 73 个内联事件属性，脚本约有 130 个 `window.*` 全局导出。v3 TypeScript 核心已经存在，但尚未成为完整 UI 的唯一状态来源。

## 3. 目标用户与核心任务

### 3.1 用户角色

| 角色       | 高频问题                             | 默认权限与界面                           |
| ---------- | ------------------------------------ | ---------------------------------------- |
| 管理层     | 网络是否健康、哪里增长、哪些点要决策 | 默认只读；总览、对比、历史、批注、报告   |
| 拓展/选址  | 候选点在哪里、依据是什么、风险多大   | 候选点、商圈、评分、情景、对比和决策记录 |
| 区域/运营  | 门店状态、异常、事件、整改进展       | 门店详情、经营趋势、事件和任务更新       |
| 数据管理员 | 数据是否完整、何时更新、字段是否匹配 | 数据源、字段映射、质量检查、备份恢复     |

不再使用一个界面同时满足所有角色。权限体系上线前，至少先提供明确的“查看模式”和“分析/编辑模式”。

### 3.2 四条主流程

#### 管理层查看与决策

1. 进入默认总览，看 KPI、异常和数据更新时间。
2. 按时间、区域、品牌、门店状态筛选。
3. 从地图或异常列表进入门店/区域详情。
4. 对比目标、趋势和历史事件。
5. 保存结论、生成管理简报或分享只读视图。

#### 门店选址

1. 选择目标城市、区域或画出研究范围。
2. 新建或导入候选点。
3. 选择商圈模型：半径圈，后续可接步行/驾车时圈。
4. 配置评价指标、方向、阈值和权重。
5. 比较候选点的市场、竞争、成本、可达性和网络影响。
6. 保存情景，记录推荐、反对意见和最终决策。

#### 业务发展复盘

1. 拖动时间轴或直接跳到某日、某月、某季度，查看当时网络状态。
2. 地图、KPI、事件流、图表和门店状态统一跟随当前时间。
3. 播放时间轴，查看开店、关店、迁址、区域扩张和经营指标变化。
4. 选择起止时间，对比新增、关闭、状态变化和经营差异。
5. 打开关键事件、关联门店、责任人、附件和原始依据。
6. 固化为复盘视图或汇报章节。

#### 经营事件和数据录入

1. 在时间轴上点击“记录”，或在地图上选中门店后点击“新增记录”。
2. 选择事件、经营数据、状态变更、计划/目标或决策五种记录类型。
3. 填写发生时间；持续性事项可填写开始和结束时间，计划可填写预计时间。
4. 关联门店、候选点、区域或多个对象，并填写结构化字段。
5. 保存后立即出现在时间轴、地图和对象详情中；支持复制上期数据和批量表格录入。
6. 更正时创建修订记录，不静默改写已被汇报引用的历史事实。

### 3.3 时间浏览交互参考

公开资料中“爱历史”同时指向文章型网站；用户描述的体验更接近[全历史的历史年表与时空地图](https://mp.allhistory.com/)、[历史地图：左图右史](https://apps.apple.com/cn/app/%E5%8E%86%E5%8F%B2%E5%9C%B0%E5%9B%BE-%E5%B7%A6%E5%9B%BE%E5%8F%B3%E5%8F%B2/id1609910044)一类产品。这里借鉴的是交互方法，而不是历史内容：

- 时间不是筛选框，而是地图的主控制轴。
- 可拖动、点击、输入日期，也可按日/月/季/年缩放时间粒度。
- 重要事件在轴上形成节点和密度提示，点击后地图定位并打开事件卡。
- 播放时地图状态连续变化，可暂停、调速和跳到下一个重要事件。
- 人物线、战争线式的“专题线”映射为门店线、区域线、项目线和策略线。
- 当前时间、比较区间和实时/历史模式必须始终醒目，避免把历史数据误认为当前数据。

## 5. 新信息架构

### 5.1 一级导航

1. **总览**：管理层默认首页。
2. **门店网络**：查看、筛选、比较现有门店和区域。
3. **经营时间**：事件和数据录入、时间浏览、状态回放、趋势与前后对比。
4. **选址模型**：候选点、商圈、自定义模型、排名、情景和决策。
5. **数据中心**：导入、字段映射、数据质量、更新记录和备份。

“地图设置、样式、绘图、图层、代码编辑器”等不再作为一级模块。

### 5.2 桌面端建议布局

```text
┌ 工作区/项目 ─ 总览 门店网络 经营时间 选址模型 数据中心 ─ 搜索 ─ 记录/分享 ┐
├ 时间范围 ─ 区域 ─ 品牌 ─ 门店状态 ─ 更多筛选 ─ 数据更新于 10:30 ───────┤
│ KPI：门店数 | 新开/关闭 | 营收/目标 | 同店增长 | 异常门店 | 待决策事项      │
├──────────┬──────────────────────────────┬──────────────────────────┤
│ 地图内容  │                              │ 洞察/详情                  │
│ 现有门店  │            地图              │ 异常、机会、门店或候选点    │
│ 候选点    │                              │ 指标、趋势、事件、操作      │
│ 竞品/商圈 │                              │                            │
├──────────┴──────────────────────────────┴──────────────────────────┤
│ 结果抽屉：门店列表 | 趋势 | 候选点对比 | 变化明细                         │
├────────────────────────────────────────────────────────────────────┤
│ ◀ 2025-01 ━━━●━━━━ 2025-06 ━━━◆开店━━━ 2025-12 ▶  1×  +记录  A/B  │
└────────────────────────────────────────────────────────────────────┘
```

### 5.3 交互原则

- **查看优先，编辑后置**：默认状态不出现清空、删除、代码编辑和绘图工具。
- **业务语言优先**：使用“现有门店、候选点、商圈、竞品、决策记录”，减少“Feature、Layer、GeoJSON”。
- **渐进披露**：地图上只保留缩放、回到全局、测距和图例；其他设置进入“地图外观”。
- **上下文操作**：选中门店才显示门店动作，进入选址模块才显示画范围和新建候选点。
- **单一入口**：导入导出只在数据中心；地图截图和简报只在分享；删除只在对象详情。
- **状态可见**：始终显示工作区、筛选条件、时间范围、数据来源和更新时间。
- **时间一致**：时间轴是共享状态；改变时间后地图、KPI、图表、表格和详情必须同步。
- **事实与计划分开**：已发生、计划中、预测值使用不同视觉编码，不允许混在同一数值中。
- **就地记录**：用户在地图对象、时间轴或表格中均可新增记录，但统一进入同一 RecordStore。
- **安全可撤销**：批量删除、替换导入和清空工作区必须预览影响，并支持撤销或恢复。
- **结果可解释**：所有分数、排行、异常和推荐都能展开查看依据。

### 5.4 当前功能的重新安置

| 当前功能          | 新位置与名称                                                   |
| ----------------- | -------------------------------------------------------------- |
| 地图控制          | 拆分为全局筛选、地图外观和上下文工具，不保留大而全控制面板     |
| 图层面板          | “地图内容”，只显示现有门店、候选点、竞品、商圈、区域等业务图层 |
| 点聚合            | 根据缩放和数据量自动开启，地图外观中保留高级开关               |
| 放大/缩小         | 使用标准地图控件，不占侧栏按钮                                 |
| 绘图工具          | 选址分析和数据维护中的上下文工具条                             |
| 显示所有标签      | 地图外观中的标签密度：自动/全部/关闭                           |
| 搜索与坐标定位    | 顶部统一搜索；坐标输入放入新建点位                             |
| 底图切换          | 地图右下角“地图外观”                                           |
| GeoJSON/Excel/CSV | 数据中心的“添加数据”和“导出/备份”                              |
| 历史地图/快照     | 经营时间中的时间点、检查点、播放和 A/B 对比                    |
| 图层存档          | 工作区版本；代码存档移入开发者工具                             |
| 自定义组          | 业务集合、区域包或临时对比集                                   |
| 战略事件追踪器    | 统一经营记录，包含事件、数据、状态、计划和决策                 |
| 数据表格          | 底部结果抽屉，与当前模块和筛选同步                             |
| 数据看板          | 总览 KPI、趋势、区域排行和异常，而非标记计数                   |
| 属性编辑器        | 门店/候选点详情抽屉，按业务字段分区                            |
| 弹窗配置          | 管理员的字段展示模板                                           |
| 分享截图          | 分享当前视图、导出图片、管理简报                               |
| 清空所有图层      | 数据中心“危险操作”，不出现在日常界面                           |

### 5.5 响应式策略

- **≥1280px**：完整三栏决策工作台。
- **1024–1279px**：地图内容折叠为图标栏，右侧详情保持。
- **768–1023px**：地图全屏，筛选和详情使用抽屉，结果使用底部面板。
- **<768px**：管理层只读查看、搜索、筛选、门店详情和简报；不承诺完整选址建模与绘图。

## 6. 业务对象与数据模型

### 6.1 从“要素”升级为“业务对象”

GeoJSON 继续作为空间交换格式，但不再承担完整业务数据库职责。建议工作区 schema v2 至少包含：

```text
Workspace
├─ locations          门店、候选点、竞品、仓库等位置实体
├─ areas              商圈、行政区、经营区域、自定义研究区
├─ metricSeries       营收、订单、客流、利润等按期指标
├─ records            事件、指标、状态、计划和决策的统一时间记录
├─ eventSeries        门店线、区域线、项目线和策略线等专题时间线
├─ selectionModels    选址模型定义、指标、公式、版本和发布状态
├─ selectionScenarios 候选点、模型版本、输入、假设和计算结果
├─ decisions          结论、理由、责任人、状态和证据
├─ savedViews         筛选、地图视图、图层和简报书签
├─ dataSources        来源、更新时间、行数、校验结果和版本
└─ audit              重要修改和迁移记录
```

### 6.2 门店与候选点基础字段

必须有稳定的 `locationId`，不能用名称或 Leaflet 运行时 ID 关联经营数据。

| 类别     | 建议字段                                          |
| -------- | ------------------------------------------------- |
| 身份     | locationId、名称、类型、品牌、业态、区域          |
| 生命周期 | 状态、筹备/开业/停业/闭店日期、状态生效时间       |
| 空间     | 经度、纬度、地址、行政区、商圈、面积              |
| 责任     | 区域负责人、运营负责人、拓展负责人                |
| 选址     | 租金、合同期、CAPEX、停车、可见性、交通、竞品距离 |
| 数据治理 | 来源、外部 ID、更新时间、数据质量状态             |

### 6.3 统一时间记录模型

事件和数据虽然展示方式不同，但共享一套时间、空间、对象和审计语义：

```text
BusinessRecord
recordId | recordType | title | validFrom | validTo | recordedAt
entityRefs[] | areaRef | geometry | status | sourceId | revisionOf
payload | tags[] | attachments[] | createdBy | confidence
```

- `recordType`：`event`、`metric`、`state-change`、`plan`、`decision`。
- `validFrom/validTo` 表示业务发生或生效时间，`recordedAt` 表示何时录入，二者不能混用。
- 瞬时事件的 `validTo` 为空；装修、活动、闭店整改等使用时间段。
- `entityRefs` 可关联一个或多个门店、候选点、区域或选址情景。
- `revisionOf` 用于更正链，保证历史引用和审计稳定。
- `confidence` 区分已确认、估算和预测数据。

事件模板支持管理员配置必填字段，例如“开店”要求开业日期、门店、负责人和依据；“竞品进入”要求品牌、位置和发现日期。

### 6.4 经营指标采用长表

后期接经营数据时，不把每个月份做成新的 GeoJSON 属性。建议采用：

```text
MetricObservation
recordId | locationId | periodStart | periodEnd | metricKey | value
unit | target | actuality | sourceId | recordedAt | revisionOf
```

首批建议指标为营收、订单、客流、客单价、转化率、毛利、经营利润、目标达成率和同店增长。指标字典必须定义单位、周期、聚合方式和缺失值含义。

录入提供三种效率层级：

- 单条快速记录：适合事件、状态变化和临时备注。
- 周/月批量表格：适合经营者按门店录入同一批指标，支持复制上期与键盘粘贴。
- 文件/API 同步：适合总部经营数据，导入前完成字段映射和质量预览。

### 6.5 历史不能只依赖快照

- 门店状态使用带生效时间的变更记录。
- 经营数据按日/月保留观测值。
- 业务事件保留发生时间、影响范围、说明和证据。
- 快照用于“管理层认可的检查点”和展示，不作为唯一历史事实。
- A/B 对比由稳定 ID 计算新增、删除、状态变化、属性变化和指标变化。
- 时间查询采用“截至当前时刻有效”的状态重建规则，而不是简单显示时间戳之前的所有记录。
- 删除历史记录采用作废标记并保留修订链，除非是尚未发布的草稿。

### 6.6 自定义选址模型体系

选址不是一个固定评分面板，而是“模型定义—发布版本—分析情景—结果复盘”四层结构。

#### 模型定义

```text
SelectionModel
modelId | name | description | applicableRegion | businessFormat
criteria[] | constraints[] | aggregation | outputScale
version | status(draft/published/retired) | createdBy | publishedAt

Criterion
criterionId | name | sourceField | unit | direction
normalization | weight | missingPolicy | expression | explanation
```

每个指标可配置：

- 指标支持正向、反向、目标值和硬阈值四种影响方式。
- 数据可来自候选点字段、空间计算、商圈聚合、经营数据或外部数据源。
- 归一化支持最小最大、分位数、目标区间、分段评分和自定义公式。
- 可设置必选条件、否决条件、指标组权重和组内权重。
- 缺失值可选择报错、淘汰、按中性值、按最差值或人工补录。
- 简单模式使用表单配置；高级模式才显示公式，公式使用受限表达式语言，禁止执行任意 JavaScript。

#### 模型运行与解释

- 模型发布后生成不可变版本；已完成情景始终引用当时版本。
- 运行前展示数据完整度、使用的数据时间和无法计算的候选点。
- 每个候选点展示总分、单项贡献、淘汰原因和原始值。
- 情景保存全部假设，允许复制后调整权重进行 What-if 对比。
- 支持 3–5 个候选点雷达图、贡献瀑布图、原始值表和地图商圈并排比较。
- 用历史已开门店回测模型，比较选址得分与开业后实际业绩；回测不会自动改权重。
- 后续有足够样本后，可增加统计/机器学习预测作为一个指标，但不能替代规则解释。

#### 建议内置模板

- 商场店：客流与客群匹配、商场能级、同业竞争、租金、楼层和可见性。
- 临街店：人口/工作人口、道路可达性、POI、竞品、停车、租金和展示面。
- 社区店：社区覆盖、家庭客群、步行可达、现有网络空白和配送便利。
- 空白模板：完全由企业自行定义。

### 6.7 数据安全边界

GitHub Pages 只能承载公开演示数据。接入真实经营数据前必须完成以下任一方案：

1. 企业内网或本机离线单文件，仅通过受控文件分发；或
2. 私有部署、登录、角色权限、服务端存储和审计。

当前“分享链接”会在小数据场景把 GeoJSON 写入 URL，真实业务模式必须禁用此行为。浏览器 localStorage 也不适合大量时序数据和附件，本地优先迁移到 IndexedDB，服务化后再接后端数据库。

## 7. 版本路线图

下列排期假设 2 周一个 Sprint、1–2 名前端、产品/设计可参与评审；v3.4 起需要后端或数据工程支持。单人开发建议将时间估算扩大约一倍。

| 版本        | 产品主题             | 预计投入    | 可交付价值                                     |
| ----------- | -------------------- | ----------- | ---------------------------------------------- |
| 规划 Sprint | 数据字典与交互原型   | 1 Sprint    | 冻结对象、任务和首屏，不急于改代码             |
| v3.1.0      | 决策工作台与门店对象 | 2 Sprints   | 管理层能看懂现状，编辑工具不再干扰             |
| v3.2.0      | 经营时间与便捷录入   | 2–3 Sprints | 能沿时间录入、查看和回放事件及经营数据         |
| v3.3.0      | 自定义选址模型 MVP   | 3 Sprints   | 企业可配置、发布、运行和解释自己的选址模型     |
| v3.4.0      | 经营数据接入         | 2–3 Sprints | 地图与 KPI、趋势、异常和区域表现联动           |
| v4.0.0      | 私有服务与协作       | 3+ Sprints  | 登录权限、共享工作区、评论审批、审计和数据同步 |

### 7.1 规划 Sprint：先确认真实任务

交付物：

- 访谈 3–5 位管理层、拓展和运营用户。
- 收集 5 个最近真实发生的选址或门店调整决策。
- 确认门店主数据、候选点表、至少 12 个月经营指标样表及现行选址评分表。
- 完成总览、时间浏览与录入、门店详情、自定义模型和选址比较五张低保真原型。
- 用脱敏数据生成 30–100 家门店的标准演示工作区。

退出条件：用户能用原型在 5 分钟内完成一次“发现问题—查看证据—形成结论”。

### 7.2 v3.1.0：决策工作台与门店对象

范围：

- 新应用壳、一级导航、统一筛选、数据更新时间和查看/编辑模式。
- 将 GeoJSON 点规范为门店、候选点等位置对象并补稳定 ID。
- 总览 KPI 框架、区域/状态统计、异常占位规则。
- 业务化“地图内容”、右侧对象详情、底部结果抽屉。
- 合并重复入口，危险操作移入数据中心。
- 保留 Full/Lite URL、离线单文件和现有导入导出兼容。

验收：

- 管理层首次进入 30 秒内能说出门店数、主要区域、状态分布和数据时间。
- 常用筛选、查看详情和返回全局均不超过 2 次点击。
- 默认界面不出现清空、代码编辑器和整套绘图工具。
- 1440×900 下无相互遮挡的常驻浮层，未预期控制台错误为零。

### 7.3 v3.2.0：经营时间与便捷录入

范围：

- 全局时间轴、日期直达、日/月/季/年粒度、播放速度和关键事件。
- 统一记录表单：事件、经营数据、状态变更、计划/目标和决策。
- 时间轴录入、地图对象录入、复制上期和批量表格录入。
- 门店线、区域线、项目线和策略线等专题时间线。
- A/B 对比：新增、关闭、迁址、状态/属性变化。
- 门店生命周期和区域扩张统计。
- 变化列表与地图双向定位。
- 保存“历史故事视图”，供管理层复盘。

验收：

- 经营者能在 30 秒内给当前门店新增一条带时间和类型的事件。
- 用户能在 5 分钟内完成一批月度指标的复制、修正和提交。
- 拖动时间后，地图、KPI、事件、图表和表格使用同一个时间上下文。
- 3 次点击内完成任意两个时间点的比较。
- 地图、统计卡和变化列表对同一差异给出一致结果。
- 用户可从一项变化追溯到事件、时间和原始对象。
- 可区分发生时间、录入时间、计划和预测，历史更正保留修订链。

### 7.4 v3.3.0：自定义选址模型 MVP

范围：

- 新建/导入候选点，选址阶段和责任人。
- 半径商圈；可插拔接口预留驾车/步行时圈服务。
- 模型中心：新建、复制、草稿、校验、发布、停用和版本查看。
- 指标来源、正反向/目标/阈值、分段/公式、组权重和缺失值策略。
- 商场店、临街店、社区店和空白模型模板。
- 候选点排行、3–5 点并排比较、商圈重叠和简易蚕食指标。
- 情景复制、What-if、贡献解释、推荐说明、决策记录和 PDF/打印友好报告。
- 使用历史门店经营结果执行只读回测。

验收：

- 业务管理员无需改代码即可从空白模板创建并发布一个有效模型。
- 用户可在 10 分钟内使用已发布模型完成候选点导入、比较和结论保存。
- 每个分数都可解释到原始指标、规则和权重。
- 修改权重后结果即时更新，但原模型版本和原情景不可被覆盖。
- 无效公式、循环依赖、权重异常和缺失数据在运行前被阻止或明确提示。
- 报告包含模型版本、假设、数据时间、排名、贡献、地图和决策理由。

### 7.5 v3.4.0：经营数据接入

范围：

- CSV/Excel 字段映射向导、主键匹配、预览和质量报告。
- 指标字典、周期选择、目标和同比/环比计算。
- 总览 KPI、地图按指标着色/大小、区域排行、趋势和异常。
- 门店详情中的经营趋势、目标达成和事件叠加。
- DataSource 接口，为 API/数据库同步预留适配器。

验收：

- 重复导入按 `locationId + periodStart + periodEnd + metricKey` 可控更新，不产生静默重复。
- 每个数字能追溯来源、周期和更新时间。
- 缺失、重复、无法匹配和异常数值在入库前明确展示。
- 筛选条件在 KPI、地图、图表和表格中保持一致。

### 7.6 v4.0.0：私有服务与协作

范围：

- 登录、组织、角色权限和工作区共享。
- 服务端持久化、版本冲突处理、审计日志和定时数据同步。
- 位置评论、@责任人、解决状态、决策审批。
- 管理简报、只读链接、访问控制和品牌模板。
- 根据实际规模评估 PostGIS、对象存储和任务队列。

v4 之前不把真实经营数据上传到公共 Pages，也不承诺多人实时编辑。

## 8. 工程实施顺序

### 8.1 不做一次性重写

继续使用 Vite、TypeScript 和 Leaflet，按可验收的业务切片迁移：

1. 建立 `WorkspaceStore` schema v2 和稳定 ID，旧 UI 继续读兼容门面。
2. 新建应用壳、筛选状态和对象详情，只读取新 Store。
3. 迁移导入与字段映射，使所有新数据先进入统一 Store。
4. 迁移地图适配器、表格、历史和选址模块。
5. 最后删除对应旧 DOM、内联事件和 `window.*` 门面。

每迁移一个模块，都先增加端到端用例，再移除旧实现。

### 8.2 建议模块边界

```text
src/
├─ app/              应用壳、导航、路由、权限和模式
├─ domain/           门店、区域、指标、事件、情景和决策
├─ store/            WorkspaceStore、选择、筛选和迁移
├─ map/              LeafletAdapter、图层渲染和空间交互
├─ overview/         KPI、异常和管理总览
├─ network/          门店网络、详情、比较和结果表
├─ history/          时间轴、差异和播放
├─ records/          统一记录、模板、批量录入和修订链
├─ site-selection/   模型定义、规则引擎、商圈、情景、回测和报告
├─ data/             数据源、导入、字段映射和质量检查
├─ sharing/          图片、只读视图和简报
└─ ui/               通用组件、对话框、抽屉和可访问性
```

### 8.3 性能路线

- 先以 5,000 家位置对象、每店 36 个月指标作为 v3 验收规模。
- Leaflet 标记使用聚合或 Canvas 渲染，表格继续虚拟化。
- 指标按需加载和聚合，不为每个周期复制 GeoJSON。
- 超过约 20,000–50,000 个同时可见点或需要 H3/热力聚合时，再评估 MapLibre/deck.gl；不要在 v3.1 提前更换地图引擎。

## 9. 测试与产品指标

### 9.1 必须自动化的关键链路

- 旧 GeoJSON 导入后正确生成稳定业务对象，导出可兼容回读。
- 全局筛选在 KPI、地图、详情、表格和导出中一致。
- 快照迁移、A/B 差异和生命周期时间边界正确。
- 瞬时/持续事件、发生/录入时间、计划/实际和历史修订语义正确。
- 时间轴变化驱动地图、KPI、事件、图表和表格的一致查询。
- 选址模型版本、公式、权重、正反向、阈值、缺失值和情景复制结果正确。
- 历史回测不修改已发布模型或原始经营数据。
- 经营数据增量导入的主键、重复、覆盖和回滚正确。
- 查看模式不能触发编辑或危险操作。
- 离线单文件不发出应用资产请求，核心查看与编辑可用。
- 所有主要流程无未预期控制台错误，并覆盖键盘操作和常用屏幕尺寸。

### 9.2 建议产品指标

- 首次用户 30 秒内理解首屏的比例 ≥ 80%。
- 找到指定门店并查看核心信息 ≤ 15 秒。
- 创建一次 A/B 历史比较 ≤ 3 次点击。
- 给已选门店新增经营事件 ≤ 30 秒。
- 复制并提交一批月度经营数据 ≤ 5 分钟。
- 比较 3 个候选点并说明排名理由 ≤ 10 分钟。
- 选址评分解释覆盖率 100%，不存在无法展开来源的总分。
- 所有经营数字的数据来源和更新时间可追溯率 100%。
- 危险操作误触率为 0，所有批量变更可预览并恢复。

## 10. 关键风险与前置决策

| 风险                      | 处理方式                                                            |
| ------------------------- | ------------------------------------------------------------------- |
| 没有统一门店 ID           | 接经营数据前必须完成主数据清洗和 ID 映射                            |
| 选址数据来源不明确        | 将人口、客流、POI、竞品、时圈做成可插拔数据源，确认采购与许可后接入 |
| 中国坐标系差异            | 明确 WGS84/GCJ-02/BD-09，导入和地图服务边界统一转换并记录来源       |
| UI 改造继续耦合旧全局变量 | 新界面只能依赖 WorkspaceStore 和模块接口，禁止增加新全局业务状态    |
| 在数据不足时过度承诺预测  | v3.3 只做透明评分；积累历史样本后再做预测和模型校准                 |
| 自定义公式带来安全和错误  | 使用白名单函数的受限表达式、静态校验、测试样例和运行资源上限        |
| 历史事实被后续修改        | 区分业务时间与录入时间，已发布记录通过修订链更正而非静默覆盖        |
| 不同粒度数据错误聚合      | 指标字典明确日/月/季粒度、聚合函数、单位和缺失值语义                |
| 公共部署泄露经营数据      | 公共 Pages 保持演示用途，真实数据使用离线受控分发或私有服务         |
| 功能越做越多              | 每个版本只服务一个清晰决策主题，低频 GIS 能力放入高级入口           |

## 11. 下一步建议

先不要直接重画全部 UI。下一步应完成一个规划 Sprint：用真实但脱敏的门店、候选点、经营数据和事件，做出“总览、时间浏览与录入、门店详情、自定义模型、候选点比较”五个可点击原型，并让管理层、拓展和运营各完成一次任务测试。

规划 Sprint 还必须拿到两类真实样本：一份至少覆盖 12 个月的门店经营数据，以及企业目前实际使用的选址评分表/Excel。没有这两份样本，不应冻结时间记录 schema 或选址公式语言。

原型确认后，以 `v3.1.0-beta.1` 发布预览版；每个正式小版本继续产出 Full/Lite 单文件、迁移说明、更新日志、截图和浏览器回归，保持主分支始终可部署。
